# Production Roadmap: Кейс №2 — ИИ-конвейер судебных документов

> Путь от MVP до production: что уже работает, что добавится, в каком порядке, с какими затратами.

---

## 1. Что уже есть (MVP)

**Работает:**
- Детерминированный препроцессор (расчёт суммы, периода, реквизитов).
- LLM-генерация текста судебного приказа (Qwen 2.5-7B через Ollama).
- 7 зон контроля (Python-правила).
- HITL-очередь (подтверждение/отклонение).
- Генерация финального PDF.
- Синтетический датасет (50 карточек + 35 с багами).

**Стек:**
- n8n (порт 5679) — оркестратор.
- Ollama (порт 11434) — LLM.
- Python 3.10 — препроцессор, правила, PDF.
- RTX 4090 24 ГБ — GPU.

**Чего нет (production-слои):**
- Fine-tuning LoRA на данных клиента.
- RAG для регламентов клиента.
- Интеграция с ГАС «Правосудие».
- Multi-tenant.
- Мониторинг дрейфа.

## 2. Пять production-слоёв

### Слой 1: Fine-tuning LoRA на данных клиента

**Что:** адаптация модели Qwen 2.5-7B под конкретную МФО через LoRA.

**Зачем:**
- Специфика формулировок конкретного клиента.
- Типовые шаблоны, принятые в организации.
- Учёт региональной судебной практики.

**Как:**
- Датасет: **100–500 размеченных документов** от клиента.
- LoRA-адаптер: малый вес, обучается за **несколько часов** на RTX 4090.
- Хранение: адаптер отдельно от базовой модели → переключение между клиентами.

**Срок:** 2–4 недели после получения датасета.

**Стоимость:** ~20–40 GPU-часов на обучение → **750–1 500 ₽** (при 37,70 ₽/час).

---

### Слой 2: RAG для регламентов клиента

**Что:** подтягивание внутренних регламентов МФО в промпт LLM.

**Зачем:**
- У клиента есть **свои требования** к документам.
- Регламенты **меняются** → RAG адаптируется без переобучения.
- Учёт специфики: что считается нарушением именно в этой компании.

**Как:**
- Векторная база: **ChromaDB** или **Qdrant** (локально, в контуре клиента).
- Эмбеддинги: **E5** или **BGE** (русскоязычные).
- Источники: инструкции МФО, шаблоны, методички.
- Подтягивание: топ-3 релевантных фрагмента в промпт.

**Срок:** 1–2 недели после получения документов клиента.

**Стоимость:** ~10 GPU-часов на индексацию → **~380 ₽**.

**Красная линия:** регламенты клиента **не покидают контур**. Векторная база — локально.

---

### Слой 3: HITL-цикл (замкнутый)

**Что:** механизм сбора данных от комплаенс-офицера для переобучения LoRA.

**Зачем:**
- Комплаенс-офицер **подтверждает/отклоняет** каждое нарушение.
- Эти данные → **размеченный датасет** для переобучения.
- Модель **улучшается** со временем.

**Как:**
- HITL-форма: отметка «подтверждено» / «отклонено» / «доработать».
- База: накопление пар «документ → вердикт».
- Переобучение LoRA: **раз в квартал** на новых данных.

**Срок:** 1 неделя на форму + постоянный цикл.

**Стоимость:** ~20 GPU-часов в квартал → **~750 ₽/квартал**.

---

### Слой 4: Правиловый движок (расширение)

**Что:** расширение 7 зон контроля новыми правилами.

**Зачем:**
- Новые типы ошибок → новые правила.
- Региональные особенности → региональные правила.
- Изменения ГПК → обновление правил.

**Как:**
- Модульная архитектура: каждое правило — отдельный Python-модуль.
- Тестирование: на синтетике + на реальных документах HITL.
- Версионирование: правила в Git, обновление без пересборки.

**Срок:** постоянно, по мере накопления данных.

**Стоимость:** разработка + тестирование, ~10–20 часов/правило.

**Примеры новых правил:**
- Проверка соответствия ст. 131 ГПК (для исков, не приказов).
- Проверка региональной практики по конкретному судебному участку.
- Проверка на соответствие внутренним регламентам клиента.

---

### Слой 5: Интеграция с ГАС «Правосудие»

**Что:** автоматическая передача документов в суд через ГАС «Правосудие».

**Зачем:**
- Ускорение подачи (сейчас — ручная загрузка).
- Снижение ошибок ввода.
- Единый поток.

**Как:**
- API ГАС «Правосудие» (требует аккредитации).
- ЭЦП — электронная подпись юриста.
- Формат: XML по требованиям ГАС.

**Срок:** 2–3 месяца (включая юридическое согласование).

**Стоимость:** зависит от интеграции и аккредитации.

**Юридическое ограничение:** подача — **только после HITL**. ЭЦП ставит юрист.

## 3. Дополнительные production-слои

### Multi-tenant

**Что:** один инстанс конвейера на несколько МФО.

**Зачем:**
- Экономия инфраструктуры.
- Единое обновление.

**Как:**
- Изоляция данных: **отдельные БД/папки** на каждого клиента.
- LoRA-адаптеры: разные для разных клиентов.
- RAG: разные векторные базы.

**Срок:** 2–3 недели.

---

### Мониторинг дрейфа

**Что:** отслеживание деградации модели и данных.

**Зачем:**
- Суды меняют требования → модель устаревает.
- Данные клиента меняются → правила устаревают.

**Как:**
- Метрики: точность 7 зон, % HITL-отклонений, время обработки.
- Алерты: если точность падает ниже порога.
- Переобучение: автоматическое по триггеру.

**Срок:** 3–4 недели.

---

### Фильтр сложных случаев

**Что:** отделение простых документов от сложных **до** конвейера.

**Зачем:**
- Банкротство, наследство, спорные дела — не для автоматизации.
- Простые случаи (95%) — через конвейер.
- Сложные (5%) — напрямую юристу.

**Как:**
- Классификатор сложности (правила + ML).
- Развилка в n8n: `simple → конвейер`, `complex → юрист`.

**Срок:** 1–2 недели.

**Важно:** в MVP этого **нет**. Добавляется на этапе production.

## 4. Дорожная карта по времени

| Этап | Срок | Что делаем |
|---|---|---|
| **MVP** | ✅ готово | Базовый конвейер на синтетике |
| **Пилот** | 1–3 месяца | На реальных данных клиента + LoRA + RAG |
| **Production v1** | 3–6 месяцев | HITL-цикл + мониторинг + фильтр |
| **Production v2** | 6–12 месяцев | Интеграция с ГАС + multi-tenant |

**Детально:**

### Пилот (1–3 месяца)

- Получение обезличенного датасета от клиента.
- Fine-tuning LoRA на 100–500 документах.
- RAG на внутренних регламентах.
- Прогон на 1 000–5 000 реальных карточек.
- Замер метрик (см. `metrics.md`).
- Калибровка порогов.

### Production v1 (3–6 месяцев)

- HITL-цикл в боевом режиме.
- Мониторинг дрейфа.
- Фильтр сложных случаев.
- Интеграция с CRM клиента.
- Обучение персонала.

### Production v2 (6–12 месяцев)

- Интеграция с ГАС «Правосудие».
- Multi-tenant (если планируется).
- Расширение на иски (ст. 131 ГПК).
- Выход на банки и ПКО.

## 8. Итог

**MVP → Пилот → Production** — три этапа.

- **MVP:** доказательство концепции на синтетике.
- **Пилот:** реальные данные клиента + LoRA + RAG.
- **Production:** HITL-цикл + мониторинг + интеграции.

**Ключевой принцип:** каждый слой добавляет ценность, но **не заменяет** HITL. Юридический контроль человека — **незыблем**.
