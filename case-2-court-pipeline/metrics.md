# Метрики: Кейс №2 — ИИ-конвейер судебных документов

> Каждая метрика — с методологией, источником и планом валидации.
> Без методологии цифра — это маркетинг, а не инженерия.

---

## 1. Как читать этот документ

Каждая метрика имеет **четыре атрибута**:

| Атрибут | Что означает |
|---|---|
| **Значение** | Цифра или диапазон |
| **Источник** | 🔎 проверено / 🧠 экспертная оценка / ⚠️ требует валидации |
| **Методология** | Как считано / на чём основано |
| **План валидации** | Как проверим на пилоте |

## 2. Ключевые метрики

### Метрика 1: Время на подготовку одного документа

| Атрибут | Значение |
|---|---|
| **До (ручная подготовка)** | 1,5–2 часа |
| **После (с конвейером)** | 15–20 минут |
| **Экономия** | ~85–90% |
| **Источник** | ⚠️ рыночная оценка (прямых данных нет) |
| **Методология** | Косвенный ориентир — симуляция юридического отдела (согласование договора ~112 минут). Перенос на судебные приказы — экспертная оценка. |
| **План валидации** | Замер на пилоте: время от получения карточки до готового PDF, сравнение с историческими данными клиента |

**Подэтапы (для методологии):**

| Этап | До (мин) | После (мин) |
|---|---|---|
| Сбор реквизитов | 15 | 1 |
| Расчёт задолженности | 20 | 1 |
| Формирование текста | 40 | 5 |
| Проверка по чек-листу | 25 | 2 |
| Проверка HITL юристом | — | 10 |
| **Итого** | **~100** | **~19** |

**Разбивка показывает:** где именно экономия — на рутинных операциях (расчёты, реквизиты), а не на юридическом контроле.

**Обратите внимание:** HITL-проверка в «после» — **10 минут** на документ. Это **сознательно оставленное время** на юридический контроль, а не узкое место.

### Метрика 2: Возвраты и отказы судов

| Атрибут | Значение |
|---|---|
| **До (текущая статистика)** | 8–15% (мировые судьи), 11,2% (арбитраж) |
| **Целевое (после автоматизации)** | 3–5% |
| **Источник** | 🔎 судебная статистика 2024–2026 (Судебный департамент при ВС РФ) |
| **Методология** | Открытая статистика по мировым судьям и арбитражным судам. Целевое значение — оценка на основе полной автоматической проверки по 7 зонам. |
| **План валидации** | Замер на пилоте: % документов, принятых судом с первого раза, vs исторические данные клиента |

**Почему целевое 3–5%, а не 0%:**
- Часть возвратов — **не** из-за формальных ошибок (например, возражения должника).
- Суды могут менять требования.
- Часть ошибок — **вне зоны конвейера** (например, опечатки в исходных данных).

**3–5% — реалистичная цель**, а не «ноль возвратов».

### Метрика 3: Пропускная способность

| Атрибут | Значение |
|---|---|
| **Документов за ночь (8 часов)** | 400–1 000 |
| **На одной RTX 4090** | 24 ГБ VRAM |
| **Источник** | 🧠 экспертная оценка на основе бенчмарков vLLM |
| **Методология** | Расчёт: 8 часов × 60 мин / (время на документ) × коэффициент параллельности. С vLLM continuous batching — до 1 000. Без — 400. |
| **План валидации** | Замер на пилоте: количество документов, обработанных за ночь |

**Почему диапазон 400–1 000:**
- **400** — консервативно, без оптимизаций, каждая карточка последовательно.
- **1 000** — с vLLM continuous batching, параллельная обработка.

**Для средней МФО (10 000 документов/год):**
- 10 000 / 365 = **~27 документов/день**.
- 400–1 000 за ночь — **в 15–35 раз больше потребности**.
- Вывод: одна RTX 4090 **с запасом** закрывает среднюю МФО.

### Метрика 4: Экономия ФОТ юристов

| Атрибут | Значение |
|---|---|
| **До** | 12–15 юристов на 10 000 документов/год |
| **После** | 2–3 юриста |
| **Источник** | ⚠️ расчёт на основе метрики 1 |
| **Методология** | 10 000 × 1,5–2 ч = 15 000–20 000 ч/год. При 1 700 ч/год на юриста = 9–12 юристов. С конвейером: 10 000 × 15 мин = 2 500 ч = 1,5 юриста + HITL +1–2 = 2–3. |
| **План валидации** | Замер ФОТ до/после пилота |

**Оговорка:** расчёт **не учитывает**:
- Обучение юристов работе с конвейером.
- Затраты на инфраструктуру (сервер).
- Затраты на внедрение и поддержку.

**Чистая экономия** — ниже, но порядок сохраняется.

**Важно:** 2–3 юриста — это **не «остаток»**, а **сознательно сохранённый юридический контроль**. Эти люди занимаются **содержательной работой** (HITL, сложные случаи, правовая позиция), а не рутиной.

### Метрика 5: Точность LLM-генерации

| Атрибут | Значение |
|---|---|
| **Целевая точность текста** | 95%+ (нет галлюцинаций в критичных полях) |
| **Целевая точность Зоны 7 (гибрид)** | 90%+ |
| **Источник** | 🧠 экспертная оценка |
| **Методология** | LLM генерирует **текст**, но все критичные поля (суммы, реквизиты, даты) — из детерминированного препроцессора. LLM не может «выдумать» цифру. |
| **План валидации** | Ручная проверка 100 документов на пилоте |

**Ключевое:** точность **не** «сколько LLM угадала», а **«сколько документов прошли все 7 зон без ошибок»**.

---

### Метрика 6: Точность правил (7 зон)

| Атрибут | Значение |
|---|---|
| **Целевая точность зон 1–6** | 100% (детерминированные) |
| **Целевая точность зоны 7** | 90%+ (гибрид) |
| **Источник** | 🧠 по определению |
| **Методология** | Зоны 1–6 — формальные проверки, ошибок быть не может (при корректных входных данных). Зона 7 — гибрид, точность зависит от LLM. |
| **План валидации** | Прогон на 35 документах с внедрёнными багами |

**Тест на синтетике:**
- 35 документов с багами → все 7 зон должны найти **все** внедрённые баги.
- Если баг не найден — это **баг в правилах**, а не в LLM.

### Метрика 7: Стоимость обработки одного документа

| Атрибут | Значение |
|---|---|
| **GPU-время на документ** | ~30 секунд (оценка) |
| **Стоимость GPU** | 37,70 ₽/час |
| **Стоимость на документ** | **~0,31 ₽** |
| **Источник** | 🧠 расчёт |
| **Методология** | 30 сек × 37,70 ₽ / 3600 сек = **0,31 ₽**. Без учёта инфраструктуры, поддержки, разработки. |
| **План валидации** | Замер на пилоте |

**Оговорка:** расчёт **не учитывает**:
- Cold start (первый прогон).
- Простои сервера.
- Электроэнергию (включено в аренду).
- Разработку и поддержку.

**Чистая стоимость** — выше, но всё равно **на порядки ниже** человеко-часа юриста.

| Что | Почему | Когда измерим |

| Точность на реальных данных | Нет данных клиента — синтетика | На пилоте |

**Ключевое:** таблица показывает **что отложено и почему**, а не «что не можем». Каждый пункт — **сознательное решение** о границе MVP.

## 5. Почему HITL не автоматизируется

**HITL — не ограничение, а принцип.**

Автоматическая отправка документов в суд **невозможна** по трём причинам:

1. **Юридическая.** Подпись под иском — персональная ответственность юриста. Никакая LLM не может нести эту ответственность.

2. **Регуляторная.** 230-ФЗ и ГПК РФ требуют, чтобы решение о взыскании принимал человек.

3. **Этическая.** Автоматическое взыскание без человеческого контроля — риск для должников и для репутации МФО.

**Поэтому HITL — не «узкое место», а сознательная граница.** Именно это отличает ответственный LegalTech от «бездумной автоматизации».

В MVP время HITL оценивается **экспертно (10 минут/документ)** — на основе понимания процесса комплаенс-проверки. Точный замер — на пилоте с реальным юристом клиента.

## 6. План валидации на пилоте

**Этап 1 (1–2 недели):**
- Прогон на 100 реальных обезличенных карточках.
- Замер: время, точность 7 зон, % возвратов (если доступно).
- **Замер времени HITL с юристом клиента.**
- Сравнение с историческими данными.

**Этап 2 (2–4 недели):**
- Fine-tuning LoRA на размеченных данных клиента.
- Повторный замер.
- Калибровка порогов.

**Этап 3 (1–3 месяца):**
- Production-внедрение.
- Мониторинг: дрейф модели, дрейф данных.
- Переобучение LoRA раз в квартал.

## 7. Честная оговорка

**Все метрики — оценки до пилота.**

- 🔎 — открытые данные (судебная статистика).
- 🧠 — экспертные оценки и расчёты.
- ⚠️ — требуют верификации на реальных данных клиента.

**Ключевой принцип:** не выдавать оценки за факты. В портфолио — показывать **методологию**, а не только цифры. Enterprise-клиент оценит честность.
